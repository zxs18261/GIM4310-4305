## 二、问题 1：程序"卡死"（实际是进了 ROM Bootloader）

### 现象
- Keil 烧录成功；上电后串口 921600 无任何数据，RGB 不亮。

### 定位证据（openocd 读取运行中的内核）
| 检查项 | 读到的值 | 结论 |
|---|---|---|
| `PC` | `0x1FFF05F2` / `0x1FFF4B14` | 落在 **ROM 系统存储器**（0x1FFF0000~），是出厂 Bootloader |
| 向量表 `0x08000000` | `20001638 / 08000325 / 08007903 / 08007447` | **App 固件确实已正确烧录**（HardFault 向量 0x08007447 与 .axf 一致） |
| PB8 配成输入后读 `GPIOB_IDR` | `0x00004100` → **bit8=1** | PB8 = **高电平**（USB-TTL TX 空闲态） |
| `FLASH_OPTR` | `0xFFEFF8AA`，`nSWBOOT0=1` | **BOOT0 取自引脚** |
| `SCB->VTOR` | `0x00000000` | 未设置（见问题 2） |

### 根因
STM32G431CBU6（48 脚 UFQFPN）的 **`PB8-BOOT0` 是同一根物理引脚**（数据手册："The BOOT0 value may come from the PB8-BOOT0 pin or from an nBOOT0 option bit depending on the value of a user nBOOT_SEL option bit to free the GPIO pad if needed."）。本板把它复用为 **USART3_RX（CN9-RX）**，且网表显示该网络**没有外部下拉电阻**（`RX ; CN9.2 U3.46`）。

于是：上电/复位瞬间，USB-TTL 的 TX 线（UART 空闲=高）把 BOOT0 拉高 → 从系统存储器启动 → 进 Bootloader，App 永不执行。复位后 PC 落在 ROM 即为铁证。

### 修复
**① 选项字节（永久修复，推荐）**——`FLASH_OPTR` 只改 1 个 bit：
```
FLASH_OPTR: 0xFFEFF8AA -> 0xFBEFF8AA     (nSWBOOT0: bit26  1 -> 0)
含义:  nSWBOOT0=0  BOOT0 改由 nBOOT0 选项位决定
       nBOOT0  =1  内部 BOOT0 = 0 -> 始终从 Flash 启动
```
- 写前读-改-写，**RDP 保持 0xAA、写保护/PCROP 等全部不变**；
- 写入后 `OBL_LAUNCH` 生效，复位即从 Flash 启动，PB8 彻底作为 `USART3_RX`。

命令（任选其一）：
```
STM32_Programmer_CLI -c port=SWD -ob nSWBOOT0=0      # 本板实测该 CLI 写选项字节失败(校验回读仍为1)
# 本工程实际使用 openocd 按 FLASH 寄存器时序写入（见附录 A）
```

**② 临时规避**（不改芯片）：复位/上电前先拔掉 TTL 接到板子 RX 的那根线（或先上电再插串口）。

> 如需恢复 ROM Bootloader 入口（串口/DFU 升级）：把 `nSWBOOT0` 写回 1（或 `nBOOT0=0`）。

## 三、问题 2：`SCB->VTOR` 从未设置（隐患）

### 现象
即使强制跳到 App，也会很快"回到 ROM"：实测中断取向量落在 ROM。
```
halt 后:  PC=0x1FFF4B30  xPSR=0xA100001C (IPSR=28 → IRQ12)
          GPIOB -> 读取正常，说明调试通路无误
          SCB->VTOR (0xE000ED08) = 0x00000000
```

### 根因
`Core/Src/system_stm32g4xx.c` 中 `/* #define USER_VECT_TAB_ADDRESS */` 被注释（CubeMX 默认），
而 `SystemInit()` 里 `SCB->VTOR = ...` 整段位于 `#if defined(USER_VECT_TAB_ADDRESS)` 之内 →
**VTOR 恒为 0**。

- BOOT0=0 时：地址 0 别名到主 Flash，"侥幸能用"；
- BOOT0=1 时：地址 0 别名到系统存储器 → **所有中断都跳进 ROM Bootloader**。

### 修复（双保险）
| 文件 | 修改 |
|---|---|
| `Core/Src/system_stm32g4xx.c:110` | 启用 `#define USER_VECT_TAB_ADDRESS`（SystemInit 中设置 VTOR=FLASH_BASE） |
| `Core/Src/main.c`（`USER CODE BEGIN 1`） | 追加 `SCB->VTOR = FLASH_BASE;` |

验证：修复后 `VTOR=0x08000000`，`CFSR/HFSR=0`，PC 稳定落在 App（`APP_Loop` ↔ `BSP_ENC_Read`）。

## 四、问题 3①：母线电压 / 母线电流通道恒为 0（软件 bug，已修）

### 现象
- 母线供电 12V，但 VOFA 的 `Ibus`、`Vbus` 通道恒为 0，无任何波动；
- 相电流 `Iu/Iv` 有极小幅波动（因问题 3②）。

### 定位证据（直接读 ADC 寄存器）
| 寄存器 | 修复前实测 | 解码 |
|---|---|---|
| ADC1 `JSQR` | `0x000018A0` | **JL=0（只转换 1 个通道）**，JSQ1=CH12(U)，JSQ2=JSQ3=0 |
| ADC1 `JDR1..4` | `0x0FF8, 0, 0, 0` | 只有 JDR1 有值；**JDR2(母线电流)/JDR3(母线电压) 恒 0** |
| ADC2 `JSQR` | `0x000006A0` | JL=0、JSQ1=CH3(V) —— ADC2 只有 1 通道，正确 |
| ADC1 `SMPR2` | `0x00006058` | CH12=6.5、CH11=24.5、CH14=247.5 周期 —— **采样时间配置是对的** |

结论：采样时间都写进去了，但 **JL（序列长度）与 JSQ2/JSQ3 没写进去**。

### 根因
`Drivers/STM32G4xx_HAL_Driver/Src/stm32g4xx_hal_adc_ex.c` 的
`HAL_ADCEx_InjectedConfigChannel()`：

```c
if ((hadc->Init.ScanConvMode == ADC_SCAN_DISABLE) ||
    (pConfigInjected->InjectedNbrOfConversion == 1U))
{
  /* 单通道分支：丢弃 InjectedNbrOfConversion，JL 固定为 0，只写 JSQ1 */
}
else
{
  /* 多通道分支：按 rank 逐个累积 JSQ1..JSQ4，最后一次调用才写入 JSQR */
}
```

CubeMX 生成的 `Core/Src/adc.c` 中 `ScanConvMode = ADC_SCAN_DISABLE`（默认），
因此 ADC1 的三次 injected 配置调用**全部走了单通道分支**：
`InjectedNbrOfConversion` 被丢弃、`JL` 固定为 0、只写了 rank1。

> G4 的"扫描模式"并非硬件位，仅被 HAL 用作软件分支判断
> （HAL 原注释："Scan mode is not present by hardware on this device, but used by software"），
> 所以只需置位结构体成员，**无需重新 `HAL_ADC_Init`**。

### 修复
`BSP/bsp_adc.c` → `BSP_ADC_Init()` 开头：

```c
hadc1.Init.ScanConvMode = ADC_SCAN_ENABLE;
hadc2.Init.ScanConvMode = ADC_SCAN_ENABLE;
```

### 验证（修复后实测）
| 项 | 修复前 | 修复后 |
|---|---|---|
| ADC1 `JSQR` | `0x18A0`（JL=0） | **`0x016198A2`**：JL=2、JSQ1=12(U)、JSQ2=3(IBUS)、JSQ3=11(VBUS) |
| `JDR3`(母线电压) | `0` | `0x0249 = 585` → **11.43 V**（12V 供电，误差<5%） |
| `JDR2`(母线电流) | `0` | `0x0FF6 = 4086`（通道激活） |
| `vbusFilt` | 0.0 V | **11.435 V** |

## 五、问题 3②：电流采样前端零流即饱和（硬件，待整改）

### 现象与证据
RAM 实测（上电封波、零电流时标定）：
```
offsetU   = 4089.2  LSB   (4089/4096×3.3V = 3.294V)
offsetV   = 4087.8  LSB
offsetBus = 4087.5  LSB
adcMeas.CurSat = 1        (贴轨标志)
```
满量程 4096≈3.3V，**三路运放零流输出全部贴在正轨（≈3.29V）**，
所以 `I = (raw - offset) ≈ 0`，电流通道看起来"没数据/很小"。

### 电路分析（以 U 相 OP3 为例，其余相同）
```
IU+ ──R37(1k)──┬── OP3_VINP ── R40(10k) ── AVCC(3.3V)
               │               R41(10k) ── AGND
IBUS+ ─R38(1k)─┴── OP3_VINM ──┬── R39(24k 反馈) ── OP3_VOUT
```
设 `Rf=R39=24k`、`Rin=R37=R38=1k`，则输出：

```
VOUT = (VINP 节点) × (1 + Rf/Rin) − IBUS+ × (Rf/Rin)
```

`VINP` 节点的戴维南等效：`R40‖R41 = 5k`、开路电压 `Vth = AVCC/2 = 1.65V`，
再经 `R37=1k` 被 `IU+(≈0V)` 拉低：

```
VINP = 1.65 × 1k/(1k+5k) = 0.275 V
VOUT(零流) = 0.275 × 25 = 6.875 V  →  超出轨，饱和到 ≈3.29V   ❌
```

**平衡差放的正确条件**：`R40‖R41 = Rf = 24k`，且分压应为 AVCC/2：

```
R40 = R41 ≈ 47k ~ 48k   →  VINP(零流) = 1.65 × 1/25 = 0.066V
                          VOUT(零流) = 0.066 × 25 = 1.65V  ✅ = 半量程 2048 LSB
差模增益 = Rf/Rin = 24（不变）
```

### 结论与整改建议
| 项 | 现状 | 应为 |
|---|---|---|
| R40、R41（OP3/U 相） | 10k / 10k | **47k~48k / 47k~48k** |
| R45、R29（OP1/母线） | 10k / 10k | 47k~48k / 47k~48k |
| R35、R36（OP2/V 相） | 10k / 10k | 47k~48k / 47k~48k |
| R37/R38/R42/R43/R30/R33（输入 1k） | 1k | 不变（决定增益） |
| R39/R44/R34（反馈） | 实物 24k | 不变（增益 24） |

> 请先在实物板上用万用表**核对该 6 个电阻的实际值**（原理图/网表标 10k）。
> 若确为 10k，改成 47k 后，零流偏置应回到约 2048 LSB，电流采样即恢复正常。
> （固件侧只做了 24 倍增益修正与偏置实测标定，无法弥补该直流工作点错误。）

### 固件侧的辅助诊断（已加入）
- 状态打印新增 `adc raw : U=.. IBUS=.. VBUS=.. V=.. [LSB]`；
- 零流偏置越界（<500 或 >3600）时打印
  `[WARN] CSA zero-current offset near rail -> current sampling saturated; check bias resistors R40/R41 (should be ~47k)`；
- `adcMeas.CurSat` 置 1 表示任一电流通道贴轨。
